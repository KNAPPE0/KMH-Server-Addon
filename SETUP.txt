KMH Server Addon - setup
========================

Extract this zip into your server folder, next to the RWT server:

    your-server-folder\
        GameServer.exe        <- the official RimWorld Together server
                                 (named RTServer.exe on newer RWT builds)
        KMHServerAddon.exe     <- this (run it)
        KMH-Data\              <- created on first boot; the zip seeds its Icons
        Tools\                 <- get-media-tools, if you want in-game video

Then run KMHServerAddon.exe (NOT the RWT server).

There are two downloads per platform, and which one you took decides what is in
the zip:

  KMHServerAddon-v1.3.0-<platform>.zip
    One KMHServerAddon.exe with everything inside it. Needs .NET 8 on the host.

  KMHServerAddon-v1.3.0-<platform>-selfcontained.zip
    Carries .NET 8 with it, so nothing to install - but it is a folder of files,
    and KMHServerAddon.exe is only a small launcher that will not start without
    them. Extract the whole thing and keep it together.

Either way it works with the RWT server you put next to it, adds the KMH
features, and starts the server. It detects which server version it sits next to
and uses the matching build automatically, identifying that server by what the
file actually contains rather than by its name - so a renamed or panel-mangled
server file is still found.

Supported RWT releases (all verified for this version):
  26.8.31.1, 26.8.16.1 (1), 26.8.16.1, 26.8.9.1, 26.7.25.1,
  26.6.23.1, 26.6.9.1, 26.6.8.1, 26.5.24.1
26.5.24.1 is the OLDEST supported release. RWT moved a core network type below
that point, so 26.4.18.1 and older are a different generation and are not
supported - on those KMH refuses to start and says so, leaving RWT running.

On RWT 26.6.23.1 and newer, RWT chat is not a reliable KMH carrier -
keep the KMH API transport enabled (the default since v1.2.0); it's the
recommended/required path there.
On first run it creates KMH-Data/ (configs + state), kmh-extensions/, and a
small .rwt-runtime/ cache next to itself.

Requirement
-----------
The .NET 8 runtime installed on the server:
    https://dotnet.microsoft.com/download/dotnet/8.0
(KMH patches RWT with Harmony, which needs the JIT from a normally-installed
runtime - it can't reach the one baked inside the self-contained GameServer.exe.
That's the one thing the owner installs once.)

If no RWT server is in the folder, KMH says so and stops. It prints every file
name it looked for, which one it picked, and why it skipped the others - so a
"not found" is always explainable.

After an RWT update KMH re-reads the server automatically; its .rwt-runtime/
cache is keyed to the exact server file, so a stale cache can't survive an
upgrade. Deleting .rwt-runtime/ is always safe - it is rebuilt on next start.

Updating to 1.3.0
-----------------
Update EVERY player's KMH-Patch mod to 1.3.0 alongside the server. The wire
protocol is v2, the same as 1.2.x, so the two generations talk and a 1.2.x
client is NOT locked out - it connects, KMH turns on, and it simply does not
show the 1.3.0 features, because each side advertises what it can do rather
than checking a version number. That is deliberate, but it means an old client
looks healthy while quietly missing the new screens, so nobody will report it.
Update the server first, then players; back up KMH-Data before the first 1.3.0
boot (the server also auto-backs-up on boot by default) and run
'kmh validate all' afterward.

The "KMH disabled: server protocol vX vs your vY" notice only appears if the
protocol number itself ever changes, which it has not since 1.2.0.

No .NET 8 on your host, or no internet on it to go and get one? Managed panels
often pin an older runtime. Grab the "-selfcontained" zip for your platform
instead - it carries .NET 8 inside it, so there is nothing to install and
nothing to download on the server itself. Every architecture has one:
win-x64, win-x86, win-arm64, linux-x64, linux-arm and linux-arm64.

Either way, extract the WHOLE folder and run the exe from inside it. The normal
build is a single executable with its dependencies inside it, but it still ships
KMH-Data alongside (icons and notes), and the "-selfcontained" build also lays
the whole .NET runtime beside the exe. Copy only the executable out of the
folder and you lose those files.

On Linux the file is named KMHServerAddon with no extension, and a zip cannot
carry the execute bit, so make it runnable once after extracting:
    chmod +x KMHServerAddon
    ./KMHServerAddon
Without that first line the host reports "Permission denied" and nothing starts.

Managed / panel hosts (Bisect, Pterodactyl, etc.)
-------------------------------------------------
These run a fixed launcher (usually GameServer.exe) every start, so they never
run KMHServerAddon.exe. Two ways to fix it:

  - If the panel lets you edit the start command, point it at
    KMHServerAddon.exe. Done - survives RWT updates.

  - If the start button is locked to GameServer.exe, swap KMH into that slot
    (KMH detects the real server under a renamed name and boots it):
        rename  GameServer.exe      ->  GameServer.rwt
        rename  KMHServerAddon.exe   ->  GameServer.exe
    Linux (no .exe):  GameServer -> GameServer.rwt ,  KMHServerAddon -> GameServer
    (then: chmod +x GameServer)
    If your RWT server file is named RTServer instead, rename that one:
        RTServer.exe -> RTServer.rwt.exe   (Linux: RTServer -> RTServer.rwt)
    KMH never mistakes itself for the server - it checks what each file
    contains, not what it is called or how big it is - so the swap is safe.
    Redo the two renames after any RWT update - it restores the stock launcher.
    On a host without .NET 8, use the -selfcontained zip for this.

KMH API transport - security & public setup
-------------------------------------------
ON by default since v1.2.0 (Config/Transport.json EnableKmhApiTransport=true,
BindAddress=0.0.0.0) - the recommended transport path for newer RWT versions.
Do not enable unsafe transport exposure. Public KMH API Transport is allowed by
default only because auth, caps, throttling, limits, and warnings are required
by default. Public bind must not mean unsecured bind.

Public setup (remote players):
  1. Forward TCP port 5099 (KmhApiPort) to the server machine, external =
     internal port number.
  2. Keep RequireKmhApiAuth=true. Every connection authenticates with a one-time
     token issued over the player's verified RWT session.
  3. After updating, run `kmh transport-test` - it self-checks the caps,
     throttle and posture and prints PASS/FAIL per guard.
Local-only instead? Set BindAddress=127.0.0.1. Chat fallback keeps KMH working
either way on RWT versions that still carry it.

Required-by-default safety (all tunable in Transport.json, all clamped so a bad
edit can't disable a guard): RequireKmhApiAuth, MaxConnections,
MaxConnectionsPerIp, AuthTimeoutSeconds, IdleTimeoutSeconds, MaxFrameKb,
FailedAuthPerIp/WindowSeconds/BlockSeconds. If you disable auth or expose the
port unsafely the server prints a loud warning at boot - public bind + auth off
is never a silent setup.

Multiple servers on one host: give each KMH instance its OWN KmhApiPort in its
KMH-Data/Config/Transport.json (like each RWT server has its own port). The server
tells the client its port in the handshake, so the client always dials the right
one - just as a player joins RWT 25554-25557, KMH connects to that server's KMH
API port. Two instances sharing a port = the second fails to bind, and it then
tells clients the transport is off rather than sending them at a port it never
opened; `kmh status` reads "ENABLED but not bound". For remote players, forward
each KmhApiPort (keep external = internal port number).

Players never type a port. The number you set in KmhApiPort is the number the
server hands out, so the one thing that has to be true is that you forwarded THAT
port. If you forwarded a different one, change KmhApiPort to match it and restart
- do not ask players to change anything. `kmh status` prints the exact host and
port clients are being told to dial, which is the fastest way to confirm the two
agree. The client's own "fallback port" setting is used only for a server that
advertises none at all.

Client debug uplink (diagnosing player-side issues)
---------------------------------------------------
Players can enable "Send debug logs to the server" in the mod options; every KMH
log line from their game then lands in KMH-Data/Debug/<user>_<timestamp>.txt
(one file per player session, every line arrival-timestamped). To turn it on for
EVERYONE automatically, set DebugLogging=true in Config/Transport.json - the
handshake tells connecting clients to start uplinking (verbose logging is forced
on for their session; their saved setting is untouched). Abuse-bounded: 300
lines/min and 10 MB per player, lines truncated at 400 chars, files pruned after
14 days, folder excluded from backups.

Living world - on by default since v1.2.0
-----------------------------------------
World events and global quests now run by themselves so the server feels alive
without any owner setup:
  - World events auto-roll: considered every 4h with a 40% chance (~one event
    per 10h on average, so timing feels organic, not scheduled), lasting 3h by
    default. Types: tax holiday, market boom/crash, resource shortage, double
    worker XP, house stipend, bounty target, global weather - weights and
    allowed types are owner-tunable.
  - Global weather: a rolled event applies a real GameCondition (aurora,
    eclipse, cold snap, heat wave by default) to EVERY colony for the duration.
    Fully data-driven via World.json WeatherConditionDefs entries of
    "GameConditionDef|Title|Description" - add any vanilla or modded condition
    def, no code needed. Fire one manually: kmh event world_weather [minutes]
    [0] [DefName].
  - Global quests auto-generate: considered every 12h, up to 2 active, 24h
    duration. Rewards are real silver from the house pool (seeded once on new
    servers), scale with the live economy, and are floored/capped
    (QuestMinReward/QuestRewardMaxReward) so quests never spam worthless or
    economy-breaking payouts.
  - Everything announces once in-game and (if configured) to the Discord
    Announcements channel when it fires/completes - no periodic spam.

  - Generated content: by default 60% of auto-generated quests are synthesized
    from YOUR server's live item catalog (items + prices reported by clients) -
    "Shortage: cloth", "Supply Run: steel" - instead of the premade templates.
    Tune with GeneratedQuestChance (0 = templates only), the value band
    (GeneratedItemMinValue/MaxValue) and GeneratedQuestGoalValue.
  - Global-quest balance (v1.2.0): hunt/build goals now SCALE with active players
    so a quiet server isn't asked for 58 kills. goal = clamp(GlobalQuestBaseTargetCount
    + activePlayers * GlobalQuestTargetsPerActivePlayer * difficulty, Min, Max)
    (GlobalQuestMinTargetCount/MaxTargetCount, GlobalQuestDifficultyMultiplier). Set
    GlobalQuestScaleByActivePlayers=false for the old fixed 20-60 goal. Default
    duration is now GlobalQuestDefaultDurationHours=48 (clamped 24-72). Auto-gen is
    skipped below GlobalQuestMinActivePlayers, and the same target isn't reused within
    GlobalQuestRepeatTargetCooldownHours. Reward pool adds GlobalQuestRewardPerTarget
    per goal unit; co-op payout is split BY CONTRIBUTION (you earned 12 of 58 -> ~12/58
    of the pool). Kill counting is fixed: a direct kill counts ONCE, and a target that
    bleeds out after recent colonist damage now counts (predator/weather deaths don't).
  - Weather can be
    auto-discovered too: clients report every GameConditionDef in their game
    (mods included) into Catalog/WeatherDefs.json; set AutoDiscoverWeather=true
    to roll those as well (ExcludedWeatherDefs blocks colony-wreckers like
    toxic fallout - extend it for harsh modded conditions).

How quests verify themselves (no admin approval needed):
  - hunt:    the client counts kills of the target def (persistent tally, saved
             with the game) and auto-reports progress every ~4s; only kills made
             AFTER the quest went live count.
  - build:   the client counts standing player-faction structures of the target
             def and auto-reports growth; pre-existing buildings never count.
  - deliver: deliberate by design - players click Deliver on the quest board and
             the goods leave their colony/caravan. If the quest ends mid-delivery
             the items are deposited to their treasury instead of being lost.
  Progress reports are cumulative and resend-safe (the server keeps each
  player's max), and world snapshots are pushed to every connected player on
  change - nobody has to open a menu for their progress to count.

Per-item control (keep some, disable others) - all in Config/World.json:
  - One event type:      remove it from AllowedEventTypes, or set its Weight*
                         to 0 to stop auto-rolls but keep manual firing.
  - One weather kind:    remove its line from WeatherConditionDefs (and add its
                         defName to ExcludedWeatherDefs if discovery is on).
  - One quest objective: remove hunt/build/deliver from AllowedObjectives.
  - One quest template:  delete its line from QuestTemplates.
  - Generated quests:    GeneratedQuestChance=0.
Quieter server overall? Set AutoRollEvents=false and/or AutoGenerateQuests=false
(manual `kmh event` / `kmh worldquest` still work), or turn the whole system off
with LivingWorld=false in Config/Features.json.

Updating from 1.1.x: these recommended defaults are applied ONCE by a marker-
gated migration. Values you customized are preserved; everything the migration
touches is logged at boot ("Defaults upgrade:" lines) and summarized in a
must-read notice ~5s after startup (also posted to your Discord Admin channel
if one is configured). If you re-disable something afterwards it stays off -
the migration never re-runs.

Frontier, sites & roadworks - new in v1.3.0
--------------------------------------------
Sites gained an archetype, a condition, buildings, and a server-side director
that opens objectives on the world map without you scheduling anything.

  - Archetypes (Config/Sites.json): Farmland, Quarry, Woodland, Ranch,
    Roadworks or Custom. The archetype names the site and decides which colonist
    skill its work uses; matching it to what the site produces earns a small
    specialization bonus. Custom takes none. Sites that existed before the
    upgrade read as Custom and keep producing exactly what they produced.
  - Buildings & storage: 2/3/4 slots by tier. Production raises output, housing
    raises the worker cap, storage lets a site hold output for collection instead
    of delivering every cycle. Held goods are the owner's OFF-MAP WEALTH - they
    count toward raid scaling and do not survive an economy reset. Only the owner
    can store at their own site; overflow always falls through to the treasury.
    Demolishing refunds nothing, so a building can never be used to park value.
  - Condition: a damaged site produces less but never nothing (output flattens
    to a floor). There is NO decay and NO upkeep chore - nothing lowers condition
    on its own. Damage comes from `kmh site-condition damage <tile>` or an
    extension; owners repair from the site's building window, priced on the damage
    actually undone.
  - Roadworks: a Construction archetype that lays persistent roads - Trail, Road,
    Highway, each unlocked by site tier. Priced per NEW segment, so crossing an
    existing road costs nothing. Silver is held while a project runs and returned
    for whatever is unbuilt if cancelled; finished road stays. Reserved silver
    counts toward raid scaling and is destroyed by an economy reset, so a project
    cannot hide wealth. Turn the system off with AllowRoadworks=false in
    Config/Sites.json. Inspect and rescue with `kmh roadworks`.
  - Frontier Operations (Config/Frontier.json): a director opens objectives -
    the first is Reclaim, restoring a derelict ruin - and hands the restored
    location to whoever contributed most, earliest. The winner chooses at claim
    time whether it becomes theirs or their guild's. Funded ENTIRELY from the
    house pool: the advertised reward is capped to what the pool can back and the
    operation does not open if that falls below the configured minimum. Nothing
    is ever minted to cover a shortfall.
    Locations are placed by asking connected clients for candidate tiles;
    matching answers from independent clients are stronger corroboration. Set
    AllowSingleProposer=false if you want that corroboration required - by
    default a small server may act on one valid proposal. Either way the server
    decides, and proposing costs and pays nothing.
    Frontier is ON by default and bounded by its spawn budget, cooldowns and
    active-location limits rather than by an off switch. Owner tooling is
    `kmh frontier` - inspect the director, list outposts, place one, step it, or
    claim on a player's behalf (refused unless that player actually earned it, so
    it settles disputes without handing anything out).
  - A captured location arrives as infrastructure, not a finished site: its new
    owner picks what it produces once, through the normal output rules and with
    no build cost. A location nobody claims goes dormant and is reused by a later
    operation instead of holding its tile forever.
  - Guild-owned sites: any current member can assign workers, build, repair,
    collect storage and set up a captured location. Leaving the guild removes
    that access at once. Production is guild income - it goes to site storage or
    the guild vault, never through whichever member opened the menu, and it does
    not inflate anyone's contribution standing. A road project stays personal to
    whoever started it: they pay, they can cancel, their escrow returns to them.

Communications - chat, mail & presence - new in v1.3.0
-------------------------------------------------------
  - KMH chat (Config/Chat.json): server-wide, per-guild and direct-message
    channels, with history on reconnect, per-user rate limits and a server-side
    log of every message.
  - Player mail (Config/Mail.json): letters carrying silver, items or
    full-condition gear. Attachments are escrowed server-side, can be recalled
    while unread, and are returned automatically if never claimed - a letter to
    someone who never logs in again cannot eat what it carried. An optional
    per-letter fee is off by default.
  - Moderation: per-player block lists filter live messages AND history, and
    staff can remove messages. A block also applies to mail.
  - Presence & playtime: the server measures time connected and, separately,
    time actually played - a paused game nobody has touched for two minutes stops
    counting, watching a raid does not. Both feed the Activity Records standings
    board and Discord's `/kmh leaderboard active`. The roster keeps whoever was
    here most recently, so a busy server stops hiding half its players.
  - Staff badges & colours (Config/Staff.json): owners, admins, moderators and
    developers are marked from YOUR role list, never from anything a client
    claims. Name, message and relay colours are per-server, and the text always
    carries the same meaning as the colour.
  - Discord chat bridge: mirrors KMH chat to a channel in either direction, each
    side independently configurable. Linked accounts post under their verified
    in-game name; a relayed message can never masquerade as native chat.

In-game video - optional, off until you add two tools
-----------------------------------------------------
Players can watch a video link without leaving the game. Your server resolves
the link, pulls it down once as a finished mp4, keeps it in KMH-Data/MediaCache
and serves that file itself. Clients only ever talk to you, never to the video
host, and the Workshop mod carries no downloader at all - which is what keeps it
Workshop-safe.

Two programs do the work and KMH does not ship them:

    yt-dlp    resolves the link
    ffmpeg    turns it into something the game can play

Miss either and the video server stays off; the boot log names the missing one.
Everything else runs as normal. They belong to other people under other
licences, so KMH fetches them for you instead of redistributing them.

The fetch script comes with the server, in the Tools folder beside
KMHServerAddon. Run it there:

    Windows   .\Tools\get-media-tools.ps1
    Linux     ./Tools/get-media-tools.sh

Both binaries land in that same Tools folder, which is where KMH looks. Setting
this up on a machine that has no server on it? The same two scripts are also
published on their own as KMH-MediaTools-v<version>.zip.

Restart afterwards and look for "Video server: using yt-dlp.exe" and "using
ffmpeg.exe". No config edit either way. KMH checks these, beside the executable
and then again inside KMH-Data: the folder itself; Tools, plus any folder inside
Tools and that folder's bin; bin; and any <folder>/bin. Unzip an ffmpeg archive
straight into Tools and it will be found - no need to dig the binary out. Point
at copies you already have with VideoHelperPath and FfmpegPath in
Config/Media.json.

NO INTERNET ON THE SERVER? Common on a locked-down host, and not a problem. Run
the script on a machine that has internet, tell it which platform you are
fetching for ('.\get-media-tools.ps1 -Rid linux-arm64'), and move the Tools
folder across however you normally move files. Nothing reaches out again once
the binaries are there.

Watch out for one thing: nobody builds a current 32-bit Windows ffmpeg any more,
so win-x86 gets yt-dlp and the video server stays off.

Ports: video is served over the KMH transport port and nothing else. KMH opens
exactly one port, ever - the one in KmhApiPort. There is nothing extra to open,
and no setting that would ask you to.

Config (KMH-Data/Config/)
-------------------------
  Economy.json          marketplace/auction/want tax, caps, price floors. Deposits are
                        client-trusted, so MaxSilverDepositPerTx / MaxItemDepositQtyPerTx
                        reject an absurd single deposit (anti-mint). Keep them generous -
                        the client removes the goods before sending, so a legit deposit at
                        or under the cap must never be rejected. 0 disables a cap.

                        ECONOMY / TREASURY ACCESS MODES. A new server generates
                        EconomyMode=Balanced; an existing config keeps whatever it has.
                        EconomyMode is a preset:
                          Standard  - remote treasury, no cooldowns/fees/caps.
                          Balanced  - remote, light 5s cooldowns + 1% deposit/withdraw fee
                                      (the generated default).
                          Localized - PersonalTreasuryAccessMode=ColonyOnly, item moves need
                                      a caravan, treasury blocked during raids.
                          Hardcore  - CaravanOnly, block during raids AND hostile map events,
                                      10s cooldowns + 2% fees.
                          Custom    - uses the granular fields below verbatim.
                        Granular fields (used when EconomyMode=Custom):
                          PersonalTreasuryAccessMode = Remote | ColonyOnly | CaravanOnly |
                                                       Disabled
                            (TreasurySiteRequired is reserved - Treasury Sites do not
                             exist yet, so it is accepted but not enforced and behaves
                             as Remote. The server warns once at boot if you set it.)
                          GuildTreasuryAccessMode    = Remote | GuildHallRequired |
                                                       CaravanNearGuildHall | Disabled
                          TreasuryDeposit/WithdrawCooldownSeconds (0 = none)
                          TreasuryDeposit/WithdrawFeePercent (0..50; silver-only
                            service fee -> the house pool, same sink as marketplace
                            tax. Deposit fee credits only when the pending deposit
                            commits; withdraw fee on success. Item deposits/withdraws
                            pay no fee. Balanced=1/1, Hardcore=2/2, others 0.)
                          MaxPersonal/GuildTreasurySilver (0 = no cap)
                          RequireCaravanForItemDeposit / ...Withdraw
                          BlockTreasuryDuringRaid / BlockTreasuryDuringHostileMapEvent
                        The client reports context (colony/caravan/raid/hostile-event/near-
                        guild-hall) with each treasury/guild action; the server enforces per
                        mode. TreasurySiteRequired still fails gracefully (behaves as Remote +
                        one-time warning) since Treasury Sites aren't built yet. Pending
                        (unconfirmed) deposits stay non-spendable regardless of mode. The boot
                        banner + 'kmh audit' show the active policy.

                        PASSIVE INCOME vs ACCESS MODES: access modes gate PLAYER-INITIATED
                        deposits/withdraws only. Earned/returned value - site rewards, and
                        marketplace / auction / want payouts and refunds - is deposited directly
                        and still accrues into the vault under any mode. Under a restrictive mode
                        the player simply can't WITHDRAW it until they meet the access rule; under
                        Disabled it accrues but stays locked until you re-enable access. This is
                        intentional (earned value is never dropped); 'kmh validate configs' prints
                        an [INFO] line whenever a non-Remote mode is set so it's never a surprise.

                        GUILD HALL RULES (P8; ALL disabled by default - standard guilds
                        unchanged). A guild's hall is a world-tile record stored ON the guild
                        (so it can't be orphaned or inherited by a reused name; disband/season
                        reset drop it with the guild). An admin sets it from the Guild Hall
                        dialog ("Set Hall here" = their current colony/caravan tile). Fields:
                          RequireGuildHallToCreateGuild          (create needs a hall tile)
                          RequireGuildHallForGuildTreasury       (guild vault needs a hall)
                          RequireGuildHallForGuildContributions  (contributing needs a hall)
                          GuildHallAccessRadiusTiles = 10        ("near" = within N tiles)
                          RequireCaravanNearGuildHallForContribution
                          RequireMemberNearGuildHallToJoin
                          AllowRemoteGuildInvites = true         (false = invite near the hall)
                        These integrate with P7: GuildTreasuryAccessMode=GuildHallRequired /
                        CaravanNearGuildHall now enforce via the client's near-hall check.
                        COMPATIBILITY: a guild with NO hall is never blocked by proximity (so
                        pre-P8 guilds keep working); the Require* flags are what force a hall to
                        exist first. Proximity is client-computed against the server-owned hall
                        tile+radius (best available - the standalone server can't do tile math).
                        'kmh audit' lists guilds missing a required hall.
  Sites.json            custom-site pricing, worker XP, cycle rate. Cost + cycle also
                        scale with amount/cycle (client can't fake amount) so an under-
                        reported item value can't buy a cheap high-output site. The server
                        uses its TRUSTED catalog value (not the client's) for build cost and
                        logs suspicious under-reports. Anti-spam caps:
                        MaxSitesPerPlayer/PerGuild/ServerWide, MaxWorkerSitesPerPlayer,
                        BuildCooldownMinutes. Worker skill from the client is advisory only;
                        server-owned site XP is authoritative. Lower CustomSiteMaxRewardAmount
                        or set AllowCustomSites=false to bound further.

                        OUTPUT TIERS (server-authoritative; UseSiteOutputTiers=true):
                        every output is classified into a tier that decides allow/block, the
                        per-cycle amount cap, cost/cycle multipliers, and how far workers can
                        scale it. Unknown/rare/tech items land in Tier 4 (DefaultUnknownOutputTier
                        =4), which ships DISABLED - so a site can NEVER print weapons, apparel,
                        tech/techprints, bionics, ammo, genes, relics, drugs, or minified
                        buildings. Tiers: 1 Basic (wood/raw/hay/meat), 2 Refined
                        (steel/cloth/blocks/meals), 3 Advanced (plasteel/uranium/gold/components),
                        4 Crafted/Rare/Tech (off). Each tier in OutputTiers[] has the same fields:
                        Enabled, Name, MaxAmount, CostMultiplier, CycleMultiplier,
                        MaxSpeedMultiplier, MaxOutputMultiplier, AllowAutoClassifiedItems,
                        Allowed/BlockedDefNames, Allowed/BlockedKeywords (Blocked* always win).
                        MaxAllowedSiteOutputTier caps the highest usable tier server-wide.
                        WORKERS = SPEED, SKILL = AMOUNT, each capped by the tier (Tier 4 never
                        multiplies output). An over-limit build amount is REJECTED (not silently
                        clamped) and the treasury isn't charged. AutoAddOwnerAsSiteWorker=true
                        makes the owner count as a worker so a solo/private site produces (0
                        workers = Paused). To allow a specific extra item, add its defName to a
                        tier's AllowedDefNames; to allow Tier 4, set OutputTiers[3].Enabled=true.
                        There is no payout timer to set: each site's own cycle time
                        (CycleMinutesPerRewardUnit, divided by worker speed) decides when it pays.
                        With UseSiteOutputTiers=false a site falls back to plain stackables only -
                        widen that with ExtraSimpleResourceDefs, or set
                        AllowUnsafeLegacySiteOutputs=true for the old unrestricted all-def
                        behaviour (admin/dev only; the server warns at boot when it is on). Old
                        Sites.json loads and gets a tier computed.
  (Treasury items)      Complex items (weapons/apparel/minified/comp/modded) are stored
                        with full state (Treasury.json item_payloads) so a deposit->withdraw
                        round-trip never cleans taint, repairs damage, rerolls quality, or
                        strips material/comp data; clean/tainted and damaged/undamaged stacks
                        never merge. Plain resources stay compact (items map). Items deposited
                        before v1.2.0's payload system load as LEGACY - their exact state can't
                        be proven, so restore-preview flags them and they never silently become
                        clean/full-value.
  Reputation.json       score deltas + tier cutoffs
  Quests.json           per-poster caps, expiry
  World.json            server event + global-quest scheduler / reward tuning
                        (auto-roll + auto-generate ON by default since v1.2.0)
  Features.json         turn major systems on/off (treasury, marketplace, guilds,
                        quests, auctions, want board, world, standings). All on by
                        default; off blocks that system server-side and clients show
                        it as disabled. Stored data is kept - re-enable to restore it.
  Chat.json             KMH chat: retention, rate limits, blocking, the image/video
                        allow-list and size cap, and the presentation colours + Discord
                        marker that ride the handshake. Presentation only - these never
                        affect permissions, identity, moderation or message contents.
  Media.json            server media resolver: the server converts formats a client
                        cannot decode (animated WebP -> GIF) and serves the result over
                        KMH's own connection. On by default, and only for those formats -
                        png/jpg/gif still load directly. Privacy: a direct load exposes the
                        PLAYER's IP to the host, a resolved one exposes the SERVER's, and
                        neither happens without the player's click-to-load choice. Bounds
                        for source/output size, pixels, frames, decoded memory and timeouts
                        all live here; the outbound fetch is https-only, allow-list checked
                        on every redirect, and refused for any private address.
  Staff.json            who is shown as staff and how the badges look. Admin is not a list
                        to maintain - RWT already knows its admins; list someone under
                        Admins only to badge a person RWT does not consider one.
  Mail.json             player-to-player mail: attachment limits, optional send fee,
                        unclaimed timeout.
  Frontier.json         Frontier Operations director: outpost and operation caps, action
                        pacing, and what a Reclaim asks for and pays. A Reclaim scales with
                        your population: ReclaimScalePerActivePlayer (0.15) adds 15% per
                        player online beyond the first, ReclaimScalePerKnownPlayer (0.05)
                        adds 5% per player who has ever joined, and ReclaimScaleMax (5.0)
                        caps the result. The SAME multiplier is applied to the material
                        cost and the silver reward, so a busy server is a bigger contest
                        rather than a better or worse deal. Set both weights to 0 for the
                        old flat behaviour.
  Enforcement.json      config-enforcement state + safe-mods list
  Maintenance.json      ServerName (this instance's friendly name - set a distinct one
                        per server on a shared host), automatic-backup + boot scan settings,
                        and ConsoleLogLevel - all (default), warn, error or quiet. It only
                        decides what the terminal is shown; KMH-Data/Debug always receives
                        every line, so turning the console down loses nothing.
  Discord/DiscordConfig.json   paste a bot token to enable the Discord bridge, or set the
                        KMH_DISCORD_BOT_TOKEN environment variable instead and leave the
                        field blank - the variable wins, and the config is never rewritten
                        with the secret. Running
                        several bots in one Discord? Set Bot.RequireMention=true so each
                        only answers !kmh-* text commands that @mention it (e.g.
                        "@KMH-25554 !kmh-link CODE") - otherwise all of them reply. Slash
                        commands are already per-bot. DMs still work without a mention.
                        Set Roles.SyncGuildRoles=true to give linked players a Discord role
                        named "<Guild> (<Rank>)" that tracks their KMH guild + rank (needs
                        the bot to have Manage Roles + its role above the ones it creates).
  (Transport and Discord have their own on/off switch in their files above.)
All are generated with defaults on first boot, and an upgrade tops each file up with
any field a new version added, keeping every value already set. Reload config live
(in-game chat or server console):  kmh reload <area|all>
`kmh config` lists what you have changed from the shipped defaults, per area; for
economy it also prints the policy actually IN FORCE, because the granular fee,
cooldown, cap and raid fields apply only under EconomyMode=Custom.
(The older reload-economy / reload-world / ... commands still work.)

Backups & recovery
------------------
KMH backs up KMH-Data/ on every boot (into a sibling KMH-Data-Backups/ folder)
and scans it for problems at startup. Owner commands (console or /kmh server):
  kmh verify              read-only integrity scan
  kmh backup [reason]     snapshot KMH-Data now    |  kmh backups   list them
  kmh restore <name|latest|before:<time>>   roll KMH-Data back to a backup
  kmh inspect <system>    dump auctions/wants/quests/... with ids
  kmh cancel <auction|want|quest> <id>   refund + remove a stuck entry
  kmh ledger [user]       recent economy audit-trail entries
  kmh smoketest           non-mutating live health check of every subsystem
  kmh support-bundle      writes KMH-Data/Support/kmh-support-<stamp>.zip: configs, the
                          status file, the latest migration report and the tail of the
                          system log, all passed through KMH's redaction (bot tokens, API
                          tokens, webhooks, passwords and signed-url signatures are masked).
                          No binaries, backups, saves, media cache or chat history. Review
                          it before sharing if you like - it is plain text inside.

Rolling back with RWT
---------------------
KMH-Data lives beside RWT's saves, not inside them, so an RWT world rollback
leaves KMH (treasury, sites, marketplace) reflecting the newer state. Bring KMH
along with a restore. It's applied at the NEXT startup - before anything loads -
and always safety-backs up current KMH-Data first, so it stays reversible.
  - By hand:  kmh restore before:<time>   then restart the server.
  - From tooling: write the target into KMH-Data-Backups/.kmh-restore-request
    (one line: a backup folder name, "latest", or "before:<iso|yyyyMMdd-HHmmss>")
    and restart. KMH consumes the marker on boot.
Pair it with an RWT rollback by matching the timestamp: KMH's boot backups are
named yyyyMMdd-HHmmss (UTC), and "before:<RWT-snapshot-time>" picks the newest
KMH backup at or before that moment. Set BackupOnBoot=true (Config/Maintenance)
so there's always a recent snapshot to land on; raise BackupRetention to keep
more history for deeper rollbacks.

Monitoring & external tooling
-----------------------------
KMH writes a machine-readable snapshot to KMH-Data/status.json on boot, every
~60s, and on demand (kmh export). It's a stable JSON contract for dashboards,
leaderboards, and health checks - read it instead of scraping internal data
files. It carries ServerName + a stable ServerId + the KMH ApiPort (so you can tell
several instances on one host apart and map bot<->server<->port), build/wire
versions, uptime, live counts (players, guilds,
marketplace/auctions/wants/quests/sites, active events + global quests), house
pool + reported wealth, current season, disabled features, the current-season
leaderboard toppers (player, colony, trade, guild, and treasury under Leaders),
and the backup list (name + UTC) for rollback correlation. Because it's rewritten
on a cadence, a
stale GeneratedUtc / file mtime means KMH has stopped - use it as a heartbeat.

Seasons
-------
  kmh season          show the current season
  kmh season roll     archive this season's leaders + all-time records, advance
                      the counter. Non-destructive - lifetime stats stay.
  kmh season reset confirm   archive leaders, THEN wipe the live economy for a
                      fresh season: treasury (personal + guild vaults), market +
                      house pool, auctions, want board, sites, quests, reputation,
                      pending mail, world events + global quests, and standings.
                      Guilds (membership + perks), Discord links, and the season
                      archive are KEPT. Backs up first, so it's reversible with
                      'kmh restore <that backup>'.
The 'confirm' word is required (it's a full economy wipe). Pair reset with a fresh
RWT scenario at season start so colony wealth also begins near zero.

Anti-cheat & enforcement
------------------------
Config enforcement (Enforcement.json): with both the addon and the KMH Patch
installed you can lock players' Mod Options to a profile you supply and keep a
safe-mods list. Turn it on with 'kmh enforce on'. This needs the patch on the
client - stock RWT clients can't be enforced.

Scenario / custom-scenario enforcement is NOT implemented yet. KMH can't force a
required scenario or block custom scenarios in v1.3.0; treat that as planned.
Until then, agree a scenario out-of-band and watch for odd starting wealth.

Save-reset economy: KMH-Data outlives a player's RimWorld save, so someone can
deposit starting resources into their treasury, reset their save, and repeat.
Two ways to handle it:
  - Automatic: set ResetEconomyOnNewSave=true in Config/Economy.json. When a
    player starts a new save/scenario, KMH clears their personal treasury AND a
    solo guild's vault (a 1-member guild is otherwise a shelter). Off by default;
    multi-member guild vaults are untouched.
  - Manual: kmh treasury-reset <user>   clear one player's personal (+ solo guild) treasury
            kmh treasury-reset all       clear every personal treasury
Both back up KMH-Data first and log what was cleared. Keep a backup before any
reset. The reset also purges the player's open marketplace listings, auctions,
and want orders (escrow lives outside the treasury and would otherwise shelter
value across a save reset); other players' bids on the reset player's auctions
are refunded. Run 'kmh audit' to spot orphaned or solo-guild vaults.

Extensions
----------
Drop extension DLLs into kmh-extensions/. See EXTENSIONS.md + the SDK bundle
(KMH.Sdk.Server) to build your own.

Client
------
Players install the KMH Patch mod (separate download); it needs RimWorld
Together + Harmony loaded before it.

Build from source
-----------------
Build the target RWT server once, point Source/Local.props or
$env:RwtServerBuildPath at its build output (for the compile-time references),
then run:  .\deploy.ps1   -> Deploy\ folder + zip in Releases\.

deploy.ps1 without -SelfContained produces the framework-dependent layout: one
KMHServerAddon.exe with the payloads, Newtonsoft, Harmony and the SDK inside it.
With -SelfContained it produces a folder instead - .NET 8 alongside a launcher
stub and KMHServerAddon.dll, which is why that zip has to be kept together.
